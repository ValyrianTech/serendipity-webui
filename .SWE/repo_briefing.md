## Project Overview

- **Name:** serendipity-webui
- **Version:** 0.1.0 (per `pyproject.toml`)
- **Description:** Standalone web interface for the Serendipity AI agent platform.
- **License:** MIT
- **Primary language(s):** Python (backend), JavaScript / HTML / Jinja2 templates (frontend)
- **Python requirement:** >= 3.12
- **Remote origin:** https://github.com/ValyrianTech/serendipity-webui.git

A standalone web UI for managing AI agents, conversations, workflows, LLM configurations, MCP servers, toolsets and system settings. The README states the Serendipity **backend server has not been publicly released yet**; this repo contains only the web UI frontend, which requires the backend to function.

Key functional areas (from README): agent management, conversations (WebSocket streaming), workflows, voice support (recording/transcription/TTS), file handling, LLM configuration, MCP server management, toolsets, dark/light mode, Bitcoin authentication (WIF key signing).

**Tech stack (declared):** FastAPI (backend), Vanilla JavaScript ES Modules + TailwindCSS (frontend), Jinja2 templating, Bitcoin WIF signing for auth, WebSocket for real-time streaming.

## Architecture Summary

**Backend (Python / FastAPI)**

The application is a single FastAPI module (`app/main.py`). It:

- Instantiates `app = FastAPI(title="Serendipity Web UI")`.
- Mounts `static/` at `/static` via `StaticFiles`.
- Configures a `Jinja2Templates` engine pointing at `app/templates`.
- Defines GET routes that return rendered Jinja2 templates (server-side HTML rendering), each named after a template file.

Routes defined in `app/main.py`:

| Route | Handler | Template |
|-------|---------|----------|
| `/` | `home` | `agents.html` |
| `/agent/{agent_name}` | `agent_home` | `agent_home.html` |
| `/agent/{agent_name}/conversations` | `conversations` | `conversations.html` |
| `/agent/{agent_name}/conversation` | `conversation` | `conversation.html` |
| `/agent/{agent_name}/edit` | `edit_agent` | `edit_agent.html` |
| `/agent/{agent_name}/workflows` | `workflows` | `workflows.html` |
| `/settings` | `settings` | `settings.html` |
| `/mcps` | `mcps` | `mcps.html` |
| `/toolsets` | `toolsets` | `toolsets.html` |
| `/skills` | `skills` | `skills.html` |
| `/llms` | `llms` | `llms.html` |
| `/scheduled-tasks` | `scheduled_tasks` | `scheduled_tasks.html` |
| `/api/tts-proxy` | `tts_proxy` | (JSON / streaming audio response) |

The only non-template backend logic is the `/api/tts-proxy` endpoint, which proxies TTS requests via `httpx.AsyncClient` (300s timeout) to an external speech server's `/synthesize_speech/` endpoint and streams the audio back. Note: the `__main__` block runs `uvicorn.run(app, host="0.0.0.0", port=8080)`.

**Frontend (JavaScript / HTML)**

- Uses **server-rendered Jinja2 templates** for page structure and **vanilla ES-module JavaScript** for client-side behavior.
- `static/js/api.js` is the API client: reads settings from `localStorage`, builds base URLs from a configurable server address/port, performs GET requests without auth and POST requests with Bitcoin signing.
- `static/js/bitcoin.js` implements Bitcoin key utilities (WIF→address, message signing) using vendored noble-style crypto libraries (`secp256k1.js`, `sha256.js`, `ripemd160.js`).
- Vendored third-party libraries under `static/js/vendor/` (mermaid, marked, highlight.js, crypto).
- `index.html` at the repo root is a large (716-line) standalone page that appears to be a prototype/reference implementation.

**Authentication model (from README):** POST requests are authenticated with Bitcoin message signing. Request payloads take the shape:

```json
{
  "message": "/sha256/{hash}",
  "signature": "<bitcoin_signature>",
  "address": "<bitcoin_address>",
  "data": { }
}
```

**Configuration model (from README):** Settings are stored in the browser's `localStorage` (server address/port, WebSocket port, WIF key, etc.). Default server port 42069, WebSocket port 8765.

**Framework:** pytest (configured in `pyproject.toml` `[tool.pytest.ini_options]`).

- `testpaths = ["unittests"]`
- `pythonpath = ["."]`

**Commands:**

```bash

# With coverage (coverage source = app)
pytest --cov=app

# Or via the configured source path
python -m pytest -q
```

Tests live in `unittests/` and use FastAPI's `TestClient` via the `client` fixture defined in `unittests/conftest.py`:

- `test_pages.py` — parametrized checks that static and agent pages return HTML, HTML-escaping of agent names, 404 handling, static file serving.
- `test_tts_proxy.py` — extensive tests of `/api/tts-proxy` (success, timeout→504, HTTP error propagation, JSON→500, param validation→422) using a mocked `httpx.AsyncClient`.
- `test_main_entrypoint.py` — verifies the `__main__` block calls `uvicorn.run(app, host="0.0.0.0", port=8080)`.

> **Observed status:** When run in the provided `.venv` (`python -m pytest -q`), the suite reports **17 passed, 17 failed**. The failures are all in `test_pages.py` and raise `TypeError: unhashable type: 'dict'` from `jinja2/utils.py` cache lookup. This is consistent with a Starlette/Jinja2 version mismatch around the `TemplateResponse` calling convention. Reported here as a factual observation; no fix is attempted.

## How to Build/Run

### Local development (from README)

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --host 0.0.0.0 --port 8080
```

Alternatively, running the module directly invokes uvicorn on port 8080:

```bash
python app/main.py
```

### Docker (from README / Dockerfile / entrypoint.sh)

```bash
docker build -t serendipity-webui .
docker run -p 8080:8080 serendipity-webui
```

The Dockerfile is a **two-stage build**:

1. **builder** (`python:3.12-slim`): creates a venv at `/opt/venv`, installs `requirements.txt`.
2. **runtime** (`python:3.12-slim`): copies the venv, copies `app/`, `static/`, `entrypoint.sh`; exposes port 8080; creates and switches to a non-root user `appuser`; sets `./entrypoint.sh` as the entrypoint.

`entrypoint.sh` launches `uvicorn app.main:app --host 0.0.0.0 --port 8080 &` and then `sleep infinity`.

### Docker image publish helper

`build_docker.py` (executable Python CLI) builds and pushes a Docker image. Argparse options: positional `docker` (image name), `--username` (default `valyriantech`), `--tag` (default today's date `%d%m%Y`), `--latest` (also tag/push `:latest`). It runs `docker build`, `docker push`, and optionally `docker tag`.

### CSS build (from build-css.sh / tailwind.config.js)

```bash
./build-css.sh            # one-shot minified build
./build-css.sh --watch    # watch mode
```

The script downloads the Tailwind CSS standalone CLI binary (`tailwindcss-linux-x64`) if not present, then compiles `static/css/tailwind.css` → `static/css/tailwind.output.css`. `tailwind.config.js` scans `./app/templates/**/*.html` and `./static/js/**/*.js`, uses class-based dark mode, extends colors with custom slate shades 850/950.
