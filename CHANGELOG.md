## [Unreleased]

### Added

- Added a regression test (`unittests/test_save_wif.py`) that runs the real `static/js/bitcoin.js` `saveWif()` through QuickJS to verify it refuses to persist an unencrypted WIF and leaves `localStorage` untouched; `quickjs` was added as a dev/test dependency.
- Added sessionStorage-based session WIF unlock: the decrypted WIF is held in per-tab `sessionStorage` (under `wif_session_key`) so it is restored on page navigation without re-prompting for the password, cleared automatically when the tab closes, and never written to disk or shared across tabs. The encrypted WIF continues to live in `localStorage`. New `saveSessionWif`/`loadSessionWif`/`clearSessionWif` helpers were added to `static/js/bitcoin.js`.
- Added a new **Lock** button in the sidebar (and `lockSession()` function) that clears the session key and returns to the unlock (or setup) modal.
- Added regression tests (`unittests/test_session_wif.py`) that run the real `static/js/bitcoin.js` session helpers via QuickJS.
- Added regression tests (`unittests/test_tts_proxy.py`) covering `/api/tts-proxy` response-size cap edge cases: a non-integer `Content-Length` header (e.g. `unknown`) is ignored rather than treated as a size, and an oversized upstream body with no declared `Content-Length` is still rejected with HTTP 502 by the post-read length backstop.
- Added a new `requireWif()` helper exported from `static/js/api.js` that returns `window.currentWif` when present and otherwise shows a 'Please unlock your WIF key first' toast (via `window.showToast`, when available) and returns `null`, plus a regression test (`unittests/test_wif_unlock_guard.py`) for the locked-WIF guard.

### Security

- The Settings page's `updateWifDisplay()` no longer slices the first and last 10 characters of the unlocked WIF private key into the `#wif-key-display` textarea (which leaked ~20 characters of key material into the DOM); it now renders a fixed `(key loaded — hidden)` placeholder and never echoes any key material into the DOM. Regression tests were added in `unittests/test_settings_wif_not_exposed.py`.
- Hardened the TTS cross-origin protection: the `/api/tts-proxy` and `/api/tts-server` endpoints now decide access solely from the `Origin` header, matched exactly (scheme + netloc) against a server-side allow-list read from the new `SERENDIPITY_WEBUI_ALLOWED_ORIGINS` environment variable; when unset it defaults to the server's own origin (see the Fixed entry). The spoofable `Referer` header and the request `Host` header are no longer used (or trusted) for the decision. When `Origin` is absent the decision is based on `Sec-Fetch-Site` (`same-origin` allowed; `same-site`/`cross-site`/`none` rejected); a request with no `Sec-Fetch-Site` and no `Sec-Fetch-Mode` is treated as a non-browser client and allowed, with `Sec-Fetch-Mode` used only as a fallback browser detector. `Origin: null` (opaque origins) is rejected unless `null` is explicitly allow-listed. Trade-off: these fetch-metadata headers are client-supplied and spoofable, so this is defence-in-depth only; a non-browser client that omits them is still allowed, which means `/api/tts-server` still returns the configured URL to non-browser clients.
- Hardened the `/api/tts-proxy` endpoint against SSRF by validating the `server` query parameter before forwarding. Only `http`/`https` schemes are allowed; when `SERENDIPITY_TTS_ALLOWED_HOSTS` is set (comma-separated list of host names) the resolved host must be allowlisted, otherwise private, loopback, link-local, reserved, multicast, and unspecified IPs (including IP literals) are blocked. Invalid/disallowed servers return HTTP 400, non-audio responses return HTTP 502, and responses larger than 25 MB return HTTP 502.
- Closed a DNS-rebinding / TOCTOU bypass of the `/api/tts-proxy` SSRF filter: for non-allowlisted hosts, the outbound connection is now pinned to the single resolved, validated IP address (with the original hostname and port preserved in the `Host` header), so `httpx` no longer re-resolves the hostname at connect time.
- The 25 MB `/api/tts-proxy` response-size cap is enforced incrementally while reading the upstream response, so an oversized body is rejected with HTTP 502 before it is forwarded to the client. Note: the upstream body is still accumulated in memory (up to the cap plus one chunk) before being returned to the client; it is not streamed straight through.
- Stopped leaking raw exception text from the `/api/tts-proxy` catch-all handler. Unexpected failures now log details server-side (via `logger.exception`) and return a generic `{"error": "Internal TTS proxy error"}` with HTTP 500.
- Fixed a stored DOM XSS vulnerability: server/agent-supplied values interpolated into template `innerHTML` (including `src`/`alt`/`title`/`value` attributes and inline `onclick` handlers) are now escaped via a shared `escapeHtml` helper that encodes `&`, `<`, `>`, `\"` and `'`. Inline `onclick` handlers that embedded untrusted values were replaced with `data-*` attributes and `addEventListener` bindings. New regression tests were added in `unittests/test_innerhtml_data_escaping.py`.
- The WIF private key is no longer persisted to localStorage in plaintext: a password is now required and the key is always stored encrypted. `saveWif()` now refuses to store an unencrypted WIF, and the unlock modal is always shown when a stored key exists.
- Sanitized the TTS text-extraction path: `getTextOnlyContent()` in `conversation.html` now routes its input through the shared `sanitizeHtml` (DOMPurify) helper before assigning to `innerHTML`, so resource-loading tags and inline event handlers (e.g. `<img onerror=...>`) in message content can no longer fire on the detached parse node used for TTS playback. Regression tests added in `unittests/test_gettextonlycontent_sanitized.py`.
- The web UI now binds to `127.0.0.1` by default instead of `0.0.0.0` (configurable via `SERENDIPITY_WEBUI_HOST`/`SERENDIPITY_WEBUI_PORT`), so the application is no longer exposed on all interfaces by default. This mitigates the previously open SSRF relay in `/api/tts-proxy` being reachable from the network.
- The `/api/tts-proxy` endpoint now rejects cross-origin browser requests with HTTP 403: the `Origin` header (falling back to `Referer`) is compared against the request `Host` header, and non-matching requests are refused (requests with neither header are treated as same-origin). This check runs before the `server` parameter SSRF validation.
- `/api/tts-proxy` public-host proxying is now disabled by default when `SERENDIPITY_TTS_ALLOWED_HOSTS` is unset; the new opt-in `SERENDIPITY_TTS_ALLOW_ANY_PUBLIC_HOST=1` flag is required to permit arbitrary public hosts, otherwise the request returns HTTP 400 (`"host not allowed"`).
- Increased the PBKDF2-HMAC-SHA256 iteration count for WIF-at-rest encryption from 1000 to 600,000, and adopted a self-describing `SCv3` blob header that stores the iteration count (followed by the 16-byte salt, 12-byte nonce, ciphertext, and 32-byte HMAC-SHA256 tag) so that raising the default count in the future never breaks blobs written with a lower count; HMAC-SHA256 authentication (encrypt-then-MAC) now covers the magic, iteration count, salt, nonce, and ciphertext. Older `SCv2` blobs (fixed 1000 iterations) and legacy AES-GCM blobs (no magic prefix) remain decryptable — `decryptWif()` dispatches on the magic prefix.
- Eliminated the `/api/tts-proxy` SSRF class by design: the endpoint no longer accepts a server URL from the client. The `server` query parameter is now an opaque selector key resolved against the server-side `SERENDIPITY_TTS_SERVERS` configuration (a JSON object mapping keys to base URLs), and the outbound request URL is built solely from that configuration, so no request-supplied value can influence the fetch target. The previous SSRF validator (`_validate_tts_server`), the IP-pinning/`Host`-header logic, and `_format_netloc_ip` were removed. Unknown selectors return HTTP 400 (`"Unknown TTS server"`); the `Origin`/`Referer` same-origin check is retained as defence-in-depth only. The `SERENDIPITY_TTS_ALLOWED_HOSTS` and `SERENDIPITY_TTS_ALLOW_ANY_PUBLIC_HOST` environment variables were replaced by `SERENDIPITY_TTS_SERVERS`.
- Closed a DNS-rebinding bypass of the TTS cross-origin self-origin fallback: when `SERENDIPITY_WEBUI_ALLOWED_ORIGINS` is empty (the wildcard-bind default), the request-time fallback derives the request's own origin from the `Host` header — but now only when the parsed host is an IP literal (IPv4/IPv6) or `localhost`/`127.0.0.1`/`::1`. A DNS hostname is rejected (and an unparsable `Host` also returns False), because a DNS name can be rebound to `127.0.0.1` by an attacker. Deployments reachable via a real DNS hostname should set `SERENDIPITY_WEBUI_ALLOWED_ORIGINS` explicitly to the real https origin(s). New regression tests were added in `unittests/test_tts_proxy.py`.
- Closed a DOM-injection bypass where thinking-block rendering in `conversation.html` split the output of `processThinkingTags()` on a fragile inline regex and injected the matching `<div class="thinking-block ...">` chunk into `innerHTML` without passing it through `sanitizeHtml` (safe only because `processThinkingTags()` happened to escape its inner text); the three duplicated call sites were consolidated into a single shared `renderMarkdownWithThinking()` helper that splits on a named `THINKING_BLOCK_SPLIT_RE` constant and routes every fragment — thinking blocks and surrounding markdown alike — through `sanitizeHtml` before building the `markdown-content` element, so no un-sanitized HTML string can reach `innerHTML`. The collapse/expand toggle was also moved from an inline `onclick` to a `data-thinking-toggle` attribute wired via a `bindThinkingToggles()` helper (since `sanitizeHtml`/DOMPurify strips inline event handlers). Regression tests were added in `unittests/test_thinking_block_sanitized.py`.

### Fixed

- Fixed two regressions introduced by the signed-message canonicalisation change: `addMessage()` in `static/js/api.js` no longer wraps `temperature` in a `Float` marker. The marker was stripped from the POSTed body by `toSignedNumbers()`, so the client signed `"temperature": 1.0` while the backend hashed `"temperature": 1` and rejected every signature with `SHA256 hash does not correspond with the data given`. The `Float` marker class and the `toSignedNumbers()` helper were removed from `static/js/bitcoin.js`, and `signData()` now returns the payload it signed, so the hashed bytes are always exactly the bytes that are POSTed. `jsonSortedEncode()` also handles `undefined` the way `JSON.stringify` does (object entries whose value is `undefined` are omitted, `undefined` array elements render as `null`) instead of throwing `TypeError: can't convert undefined to object`, which had broken `initializeNewConversation()` and the tool-request accept/reject flow. Regression tests were added in `unittests/test_signed_message_canonicalisation.py`.
- Fixed signed-message canonicalisation so the bytes the web UI signs match the backend's Python `json.dumps(obj, sort_keys=True, indent=2, ensure_ascii=False)` byte-for-byte: `jsonSortedEncode()` in `static/js/bitcoin.js` now sorts keys by Unicode code point (not UTF-16 code-unit order, which misordered astral-plane characters), uses two-space indentation with compact empty `{}`/`[]`, emits raw UTF-8 strings (escaping only `\"`, `\\` and control characters below U+0020), and reproduces CPython float `repr` semantics (`-0.0`, shortest round-trip digits, signed zero-padded exponent). The client signs exactly the JSON it POSTs (the backend hashes the data as received), so an integral value such as a `temperature` of `1` is signed and sent as the bare integer `1`. Regression tests were added in `unittests/test_signed_message_canonicalisation.py`.
- Fixed a dependency-manifest mismatch: `python-dotenv` is imported by `app/main.py` (`from dotenv import load_dotenv`) and pinned in `requirements.txt`, but was missing from `pyproject.toml`'s `[project].dependencies`. `python-dotenv==1.2.4` is now declared in `pyproject.toml` as well, so an editable install (`pip install -e .`) resolves it. Added `unittests/test_dependency_manifests.py`, which asserts that `pyproject.toml` and `requirements.txt` pin the same runtime dependency set (and that `app.main` still imports).
- Fixed the container being unreachable with `docker run -p 8080:8080`: `entrypoint.sh` now defaults the bind host to `0.0.0.0` inside the container (loopback is unreachable from outside the container network namespace) while `app.main`'s bare-metal default stays `127.0.0.1`; `SERENDIPITY_WEBUI_HOST=127.0.0.1` still restores loopback-only. The entrypoint now exports the resolved `SERENDIPITY_WEBUI_HOST`/`SERENDIPITY_WEBUI_PORT` before `exec`ing uvicorn so `populate_default_allowed_origins()` sees the same bind address uvicorn actually binds (previously the `--host` flag alone left the app believing it was on `127.0.0.1` and populated a useless `http://127.0.0.1:PORT` allow-list entry). Because a wildcard bind leaves the startup TTS allow-list empty, operators exposing the container should set `SERENDIPITY_WEBUI_ALLOWED_ORIGINS` explicitly; regression tests were added in `unittests/test_entrypoint_script.py`.
- Fixed the TTS endpoints (`/api/tts-proxy`, `/api/tts-server`) returning HTTP 403 with the default configuration: previously, when `SERENDIPITY_WEBUI_ALLOWED_ORIGINS` was unset/empty (the default), the empty allow-list rejected every request that carried an `Origin` header, including same-origin ones. The app now populates the allow-list with its own origin (`http://{host}:{port}`) at startup via a FastAPI `lifespan` handler (`populate_default_allowed_origins()`, which also logs the effective list at INFO), and `_origin_allowed()` falls back to the request's own origin (scheme + `Host`) when the allow-list is empty, so the default configuration rejects only cross-origin requests. `Host` is still never trusted to match a foreign `Origin`, and `Referer` is still never used. When `SERENDIPITY_WEBUI_HOST` is a wildcard bind address (`0.0.0.0` or `::`), `populate_default_allowed_origins()` now deliberately leaves `SERENDIPITY_WEBUI_ALLOWED_ORIGINS` unset instead of populating a browser-unreachable `http://0.0.0.0:PORT` entry, so the empty-allow-list request-time fallback (scheme + `Host`) stays reachable and legitimate same-origin requests are not rejected with 403; regression tests were added in `unittests/test_tts_proxy.py`.
- `loadWifStorage()` in `static/js/bitcoin.js` now recovers gracefully from a corrupted or non-JSON `localStorage` entry: it parses inside a `try`/`catch`, rejects non-null non-object values (e.g. `null`, `42`, `"hello"`, `true`) as corrupted, logs `Discarding corrupted WIF storage entry:` via `console.warn`, clears the bad entry with `localStorage.removeItem(STORAGE_KEY)` so the user can recover, and returns `null`, instead of throwing an uncaught `SyntaxError` that aborted page bootstrap. Regression tests were added in `unittests/test_load_wif_storage.py`.
- Template values interpolated into JavaScript string literals in several Jinja2 templates (`agent_home.html`, `conversation.html`, `conversations.html`, `edit_agent.html`, `workflows.html`) are now rendered via Jinja2's `tojson` filter, preventing JS injection/XSS from crafted template values.
- Hardened WIF private-key parsing in `static/js/bitcoin.js`: `wifToPrivateKey(wif)` previously had a dead ternary and did not validate the decoded WIF structure, so it could return a wrong/truncated key for malformed input. It now rejects any decoded payload whose length is not exactly 37 or 38 bytes (`Invalid WIF: bad length`), verifies the 4-byte Base58Check checksum via double-SHA256 (`Invalid WIF: bad checksum`), requires the mainnet version byte `0x80` (`Invalid WIF: unsupported version byte`), and for compressed WIF requires the trailing flag byte to be `0x01` (`Invalid WIF: bad compression flag`), returning exactly the 32-byte private key following the version byte. The setup UI (`app/templates/base.html`) now calls `wifToAddress(wif)` before saving settings and refuses to save an invalid WIF with the toast `Invalid WIF key: please check for typos`; the `wifToAddress` catch block now logs `Invalid WIF:` plus the error message. Regression tests were added in `unittests/test_wif_validation.py`.
- As a consequence of the WIF parsing hardening above, `signMessage()` and `signData()` in `static/js/bitcoin.js` now propagate the `Invalid WIF` exception thrown by `wifToPrivateKey()` rather than swallowing it: neither function wraps the call in `try`/`catch`, so a malformed WIF rejects the returned promise. The ~30 signing helpers in `static/js/api.js` (which import `signData` from `./bitcoin.js`) likewise do not catch, so a malformed WIF now surfaces an `Invalid WIF` error at every signing call site instead of silently signing against a wrong/truncated key. Regression tests were added in `unittests/test_wif_signing_propagation.py`.
- Fixed a DOM XSS fallback gap in `app/templates/skills.html`: the instruction/resource preview functions `updateInstructionsPreview` and the resource-preview branch of `setResourceTab` render skill/resource instructions into a preview pane, and while the `marked` branch sanitizes via `sanitizeHtml(marked.parse(...))`, the fallback branch (taken when the vendored `marked` library fails to load/parse) concatenated the raw user/agent-authored `content` straight into `innerHTML`, so a payload such as `<img src=x onerror=alert(1)>` would execute. Both fallback branches now route through the shared `escapeHtml` helper from `static/js/sanitize.js` (the second branch also defaults to `'No content'` when `content` is empty). Regression tests were added in `unittests/test_skills_preview_fallback.py`.
- The container entrypoint (`entrypoint.sh`) now runs uvicorn in the foreground via `exec` (as PID 1) instead of backgrounding it with `&` followed by `sleep infinity`; the container now reports uvicorn crashes (previously hidden), forwards SIGTERM/SIGINT for graceful shutdown, and exits with the application's status code so Docker restart policies work.
- Fixed a regression that made the web UI unusable over plain HTTP on a LAN address: the WIF-at-rest encryption used the Web Crypto `crypto.subtle` API, which browsers only expose in secure contexts (HTTPS or localhost), so saving or unlocking the key threw `Cannot read properties of undefined (reading 'importKey')`. `encryptWif()`/`decryptWif()` in `static/js/bitcoin.js` are now implemented in pure JavaScript (PBKDF2-HMAC-SHA256 key derivation + ChaCha20 + HMAC-SHA256 encrypt-then-MAC) so they work in every context; blobs written by the previous AES-GCM implementation carry no magic prefix and remain decryptable via `crypto.subtle` in secure contexts. Regression tests were added in `unittests/test_wif_encryption.py`.
- The API client in `static/js/api.js` now routes all fetch responses through a shared `parseJsonResponse()` helper: non-2xx responses throw a descriptive `Error` (`<context> failed: <detail>`, using the JSON body's `error`/`detail` when available), and successful responses that are not `application/json` throw a `non-JSON response` error, instead of ignoring the HTTP status and letting `response.json()` fail on non-JSON error bodies. Regression tests were added in `unittests/test_api_json_error_handling.py`.
- Fixed a `TypeError` thrown when signed API mutation handlers on the LLM, MCP, toolset, skill, edit-agent, and workflow pages read `window.currentWif` directly while the WIF key was locked: those handlers now call `requireWif()` and bail out early (with a 'Please unlock your WIF key first' toast) when it returns `null`, and `signData()` in `static/js/bitcoin.js` throws a clear 'WIF key is locked' error if called with no key.
- Fixed a DOM-injection gap in `app/templates/toolsets.html` where the toolset "Tool Filter" input's `value` attribute interpolated `(server.toolFilter || []).join(', ')` raw into a quoted attribute; it is now wrapped with the shared `escapeHtml` helper, and the `unittests/test_innerhtml_data_escaping.py` guardrail was tightened so a raw `.join(...)` interpolation is no longer considered safe (only join-chains that call `escapeHtml`/`sanitizeHtml` per element are allowed), with a new regression test `test_toolsets_tool_filter_is_escaped`.
- Backend API and WebSocket URLs are now derived from the page protocol instead of being hardcoded to http:// and ws://: a new getUrlScheme() helper in static/js/api.js returns https:/wss: when the UI is served over HTTPS and http:/ws: otherwise, and getBaseUrl() uses it. This fixes mixed-content failures (blocked active/passive mixed content and WebSocket upgrade failures) when the Web UI is served over TLS; note the backend API and WebSocket ports must then also be reachable over TLS. Templates (agent_home.html, agents.html, conversation.html) previously built http:// URLs inline and now call getBaseUrl(). Regression tests added in unittests/test_get_base_url_scheme.py.
- Fixed a bug in `app/templates/conversation.html` where the `window.removeOpenFile` handler called `removeStagedFile()` with the wrong signature (passing the staged-file id as the `wif` argument and omitting the data payload), so the call threw inside `signData` and the rejection was silently swallowed; the file disappeared from the local UI list but was never un-staged on the backend, so it stayed attached to the next message. The handler is now `async` and routes through the already-correct `window.removeStagedFileAt(index)` helper (which guards on `window.currentWif`, builds the `{agent, conversationId, fileName}` payload, awaits, and surfaces errors via a toast), and the staged-files display is refreshed via `updateOpenFilesList()`/`updateStagedFilesDisplay()` after load, stage, and remove. Regression tests were added in `unittests/test_remove_open_file_delegates.py`.

### Changed

- Documented when allow-listing the `null` origin in `SERENDIPITY_WEBUI_ALLOWED_ORIGINS` is legitimately needed and its security implications: `Origin: null` is a serialized opaque origin shared by every opaque-origin context (sandboxed iframes, `file://` pages, `data:`/`blob:` documents), so allow-listing the literal string `null` is an all-or-nothing, broad grant that should only be added when the UI is genuinely served from such a context (docs only; no behavior change).
- Legacy plaintext WIF entries in `localStorage` (the pre-encryption shape `{encrypted: false, data: "<raw WIF>", timestamp}`) are now detected on startup via a new `isLegacyPlaintextWif()` helper in `static/js/bitcoin.js`, cleared from `localStorage`, and the user is routed to the setup modal with an explicit message telling them their previously-stored plaintext key was removed for security and must be re-entered. Rationale: a plaintext WIF cannot be encrypted without a password and must never remain at rest, and `decryptWif()` can never succeed against a plaintext entry, so the old behaviour left such users permanently stuck on the unlock modal with no explanation.
- Added a `withWifBusy()` UI helper (in `app/templates/base.html` and `app/templates/settings.html`) that disables the unlock, setup "Save & Continue", and change-key "Save" buttons and shows an "Unlocking…"/"Encrypting…" label while the now much-slower PBKDF2 derivation runs, yielding a macrotask first so the browser can paint before the synchronous derivation blocks; the original label and disabled state are restored when the wrapped promise settles.
- Changed `unittests/vulture_whitelist.py` to use a bare-name expression statement (matching `app/vulture_whitelist.py`) and wired both whitelist files into vulture via the `[tool.vulture]` `paths` list in `pyproject.toml` (no user-visible behavior change).
- Added type annotations and docstrings in `app/main.py` and refactored `app/vulture_whitelist.py` to use a string-literal list (no user-visible behavior change).
- Added type annotations and fixed mypy errors in `app/main.py`, and resolved a vulture dead-code false positive in the TTS proxy test (no user-visible behavior change).
- Documented the new `SERENDIPITY_WEBUI_HOST`, `SERENDIPITY_WEBUI_PORT`, and `SERENDIPITY_TTS_ALLOW_ANY_PUBLIC_HOST` environment variables in `.env.example`.
- `/api/tts-proxy` now buffers the upstream response honestly instead of pretending to stream: the `client.stream(...)`-then-collect hybrid was replaced with a plain `client.get(...)` and a normal `Response`, with the 25 MB cap enforced via the `Content-Length` header (where present) and a post-read length check. The frontend (`static/js/api.js` `getTTSUrl`) no longer sends a server URL, and the editable "Voice Server URL" field was removed from the settings page (the TTS server is now server-driven). A new read-only `GET /api/tts-server` endpoint returns the resolved default server URL (`{"url": ...}`), which the agent "Initialize Voices" action now uses (via the new `getTTSServer()` client helper) instead of the removed setting.
- Removed an unused `import pytest` line from `unittests/test_thinking_block_sanitized.py` via a ruff safe auto-fix (a purely cosmetic, behaviour-neutral style change bundled into the same PR; the import was genuinely unused, ruff passes on the file without it, and no test behaviour changes).
